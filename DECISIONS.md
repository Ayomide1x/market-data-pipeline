# Decisions

## Kafka distribution / image

Chose: `apache/kafka:4.3.1`, the official upstream image, pinned to an exact tag.
Over: `bitnami/kafka` and `confluentinc/cp-kafka`.
Because: Bitnami removed versioned tags from its free Docker Hub catalog on 2025-08-28 (Broadcom's catalog restructuring) — the free tier is now `latest`-only, which is incompatible with pinning versions in the build files. `cp-kafka` is versioned against Confluent Platform releases, not Kafka releases, which obscures the actual broker version for anyone reading this file later. `apache/kafka` has been KRaft-native since Kafka 3.7, and as of Kafka 4.0 ZooKeeper mode was removed entirely, so it's also the only mode the upstream project still ships.
Breaks if: Apache stops publishing this image or changes its tagging scheme; re-evaluate at that point rather than assuming Bitnami's free tier comes back. Verified: `docker pull apache/kafka:4.3.1` succeeds (digest `sha256:77e3df9054047a88b520d0cc46e16696d3b22022e1d580aeccd2632df6532837`).

## Kafka storage formatting: rely on the image's own on-start format, no separate step

Chose: set `CLUSTER_ID` as a plain (non-`KAFKA_`-prefixed) environment variable on the `kafka` service; no separate `kafka-storage.sh format` step anywhere in the compose files.
Over: running `kafka-storage.sh format --cluster-id ... --config server.properties` as an init step (e.g. a second one-shot service, or a custom entrypoint wrapper).
Because: inspecting the image's actual startup path (`/etc/kafka/docker/launch`) shows it already calls `kafka.docker.KafkaDockerWrapper setup`, which formats storage using `CLUSTER_ID` on every start, and detects an already-formatted log directory to skip reformatting (matching on `"already formatted"` in the setup command's output). A separate manual formatting step would be redundant with what the entrypoint already does, and would fight over CLUSTER_ID sourcing.
Breaks if: nothing, as long as `CLUSTER_ID` stays a fixed value across restarts and the named volume isn't dropped — both already required by the fixed-cluster-ID decision below. Verified (partially): after `docker compose up`, `docker compose restart kafka` logs `Log directory /var/lib/kafka/data is already formatted. Use --ignore-formatted to ignore this directory and format the others.` — confirming the format-and-skip codepath runs. Note: `restart` only restarts the existing container's process, it does not recreate the container, so this only proves the skip-on-already-formatted logic fires — it does not by itself prove the data survives *container recreation* (`down`/`up`, or a container replaced by an image update). That's a stronger, separate claim; verify it with an actual `down` (no `-v`) then `up`.

## KRaft topology: single combined node

Chose: one node running both roles (`process.roles=broker,controller`), one-node quorum (`controller.quorum.voters=1@kafka:9093`).
Over: separate broker and controller containers.
Because: this project is single-broker, RF=1, multi-broker explicitly out of scope. A separate controller node is the production topology for multi-broker clusters where the controller quorum needs to survive a broker failure independently — with one broker there is nothing to fail over to, so it's pure extra config and an extra container for no benefit.
Breaks if: multi-broker is ever added later — combined mode would need to be split into a real controller quorum before adding brokers, not incrementally.

## Explicit topic creation, auto-create disabled

Chose: `auto.create.topics.enable=false` on the broker, plus a one-shot `kafka-init` Compose service, gated on `condition: service_healthy` for `kafka`, that on every run: (1) `kafka-topics --create --if-not-exists` with the full topic config, (2) `kafka-topics --describe` and checks the reported partition count equals the expected 6, exiting non-zero if it doesn't, (3) unconditionally runs `kafka-configs --alter --add-config` with the same retention/segment settings.
Over: a manual `docker compose run` step invoked by hand; leaving auto-create on; stopping at `--create --if-not-exists` alone.
Because: auto-create would create `ticks` with broker defaults (wrong partition count, no explicit retention — violates invariant #9) the first time anything produces to it. A manual step is easy to forget and isn't part of "the stack," which matters once the same compose shape needs to come up unattended after a VM reboot (Stage 10). `--if-not-exists` alone is not sufficient, though: it makes topic *creation* idempotent, but on every subsequent `up` it silently no-ops against an existing topic — so a retention/segment value changed in this file would never reach the already-running topic, which is itself a violation of invariant #9 (the running topic's config would drift from what's declared here). Re-running `kafka-configs --alter` every time closes that gap; it's a safe no-op when nothing changed. Partition count can't be fixed the same way — it's immutable after creation — so `kafka-init` checks it and fails loudly instead of silently running against a topic with the wrong shape.
Breaks if: someone bumps the partition count in this file for an already-created topic — `kafka-init` will refuse to proceed (by design; the topic must be deliberately recreated, which loses data, so that's a decision a human makes, not something automated). `restart: "no"` on `kafka-init` means a failed check stops there rather than retry-looping — confirmed by inspecting `compose.yaml`, no `restart` policy is set that would restart it.

## Partition count: 6, one topic definition for dev and prod

Chose: 6 partitions for `ticks`, same partition count and topic config used in both `compose.yaml` (dev) and `compose.prod.yaml` (prod) — one topic definition, not two.
Over: 3 (one partition per dev symbol), 12+, or separate dev/prod partition counts sized to each environment's symbol count.
Because: partition count doesn't scale with symbol count — each symbol's key always hashes to exactly one partition (invariant #1), so adding symbols never requires more partitions. What partition count actually caps is consumer parallelism: 6 divides evenly across the 2 or 3 consumer instances Stage 4 runs, so every instance gets an equal partition share with no leftover. Since partition count can never change after creation, it's set once for the topic's whole life rather than per-environment.
Breaks if: consumer instance count ever needs to exceed 6 — parallelism is hard-capped at the partition count regardless of how many instances are running. Note for Stage 4: with only 3 active symbol keys across 6 partitions, at least 3 partitions carry no traffic at any given time — the rebalance test must deliberately kill the instance that owns a partition with live traffic, not an arbitrary one, or the test will look like nothing happened.

## Retention and segment settings

Chose: `segment.ms=3600000` (1h), `segment.bytes=52428800` (50MB), `retention.ms=21600000` (6h), `retention.bytes=209715200` per partition (200MB), `cleanup.policy=delete`.
Over: leaving segment roll at the 7-day default and relying on `retention.ms` alone.
Because: retention only reclaims closed segments; a 7-day default segment roll means `retention.ms=6h` would be a no-op on a low-volume topic until a segment happens to fill or age out. Small `segment.ms`/`segment.bytes` forces segments to close often enough for time-based retention to actually execute, satisfying invariant #9.
Breaks if: **once segments are deleted under this policy, replaying from topic start no longer reproduces the full history behind the current EMA state in Redis** — `tools/verify-ema` (Stage 3) cannot assume "replay from earliest offset" reconstructs the same EMA from zero once retention has trimmed the topic. Stage 3's `verify-ema` will need to compare against Redis with a tolerance after a warm-up of several EMA time constants, rather than expecting an exact match from a cold replay. Recorded here for Stage 3; not building this now.

## Kafka listener topology

Chose: three listeners, with bind address separated from advertised address.
- `listeners=INTERNAL://0.0.0.0:9092,EXTERNAL://0.0.0.0:29092,CONTROLLER://0.0.0.0:9093` — what the broker process binds to inside the container. Always `0.0.0.0`: the container's own network namespace is already isolated by Docker, so there's nothing gained by binding narrower, and 0.0.0.0 is required for `EXTERNAL` to be reachable via a published port at all.
- `advertised.listeners=INTERNAL://kafka:9092,EXTERNAL://127.0.0.1:29092` — what the broker tells clients to reconnect to after the initial connection. `INTERNAL` for containers on the Compose network (the consumer, `kafka-init`, anything else running inside Compose); `EXTERNAL` for host-side clients (CLI tools like `kafka-console-consumer`/`kcat`, and the ingester when run via `npm run dev` outside a container). No advertised address for `CONTROLLER` — KRaft controller traffic isn't a client-facing listener. `EXTERNAL` uses the literal `127.0.0.1`, not `localhost`: Docker publishes the port on the IPv4 loopback only, but `localhost` resolves to both `::1` and `127.0.0.1`, and a client that tries the IPv6 address first gets connection-refused before ever falling back to IPv4 — this is exactly what happened when testing from macOS (below).
- `listener.security.protocol.map=INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT,CONTROLLER:PLAINTEXT` — required once listener names are custom; the broker has no built-in mapping for names it doesn't recognize.
- `inter.broker.listener.name=INTERNAL` — broker-to-broker (and this broker's own controller-adjacent traffic) uses `INTERNAL`, never `EXTERNAL`. Without this, the broker defaults to looking for a listener literally named `PLAINTEXT` and refuses to start.
- `controller.listener.names=CONTROLLER` — tells the broker which listener carries KRaft quorum traffic.

Over: a single `kafka:9092` listener; letting `listeners` derive from `advertised.listeners` by the image's own default substitution.
Because: `kafka:9092` only resolves inside the Compose network, so a single-listener setup leaves host-run tools and the ingester (when iterated on outside a container) unable to reach the broker at all. Setting `listeners` explicitly (rather than relying on the image's `configureDefaults` substitution of hosts with `0.0.0.0`) keeps bind and advertised addresses visibly distinct in the compose file instead of one being implicit.
Breaks if: `EXTERNAL`'s port mapping ships in `compose.prod.yaml` by mistake — that would expose Kafka to the public internet, violating invariant #10 (see the compose file structure decision below for how the file split prevents this).

Verified from macOS itself (not from inside a container — `docker run --network host` on Docker Desktop for Mac only reaches the Docker VM, not the Mac's own network namespace, so that earlier check proved nothing about host reachability):
- First attempt, `kcat -b localhost:29092 -L`, failed: `localhost` resolved to `[::1]:29092` first and kcat got connection-refused, because `lsof -iTCP -sTCP:LISTEN -P` showed Docker's proxy listening on `127.0.0.1:29092` only — no `[::1]:29092` listener exists, matching the `127.0.0.1:29092:29092` binding in `compose.override.yaml`.
- After changing `advertised.listeners` to `EXTERNAL://127.0.0.1:29092`, `kcat -b 127.0.0.1:29092 -L` succeeded from macOS: metadata listed broker `1 at 127.0.0.1:29092` and topic `ticks`.
- Topic survives container recreation, not just an in-place restart: `docker compose down` (no `-v`) followed by `docker compose up` recreated the `kafka` container from scratch, `kafka` reported healthy, and `kafka-init`'s describe step showed `ticks` still at 6 partitions with the same `TopicId` — the named volume and fixed `CLUSTER_ID` did what the earlier "Fixed cluster ID, named data volume" decision claimed, this time actually proven across a real recreation rather than a same-container restart.

## Fixed cluster ID, named data volume

Chose: a fixed, hardcoded KRaft cluster ID (`CLUSTER_ID=0vdKmALERBCX9QAvTQWdcg`, generated once with `kafka-storage.sh random-uuid` and committed to `compose.yaml`) and a named volume (`kafka-data`) mounted at `/var/lib/kafka/data` (overriding the image's default `log.dirs=/tmp/kraft-combined-logs` for a clearer, explicitly-owned path).
Over: generating a random cluster ID at container startup, or using an anonymous/bind-mount-free volume.
Because: a cluster ID generated fresh on every startup would fail the image's own format-on-start step against an already-formatted volume (see the storage-formatting decision above) — the log directory would be stamped with the volume's original cluster ID forever, and a new random ID on each boot would mismatch it. Compose's default anonymous volumes also get orphaned (and eventually pruned) independently of the container — either problem can silently wipe the topic and all consumer offsets on a routine `docker compose up` after a container replacement.
Breaks if: the named volume is removed with `docker compose down -v` — that's a deliberate, visible reset, not an accidental one, which is the point.

## Exchange: Coinbase, `trade_id` (not `sequence`) as `exchangeSeq`

Chose: Coinbase's public Exchange WebSocket feed (`ws-feed.exchange.coinbase.com`), `matches` channel, using `trade_id` for the Kafka message's `exchangeSeq`.
Over: Kraken's public WebSocket v2 (`wss://ws.kraken.com/v2`); using Coinbase's `sequence` field for `exchangeSeq`.
Because: both Coinbase and Kraken confirmed no-auth for public trade/ticker channels — Coinbase docs: *"Coinbase Market Data is our traditional feed which is available without authentication"*; Kraken docs: *"public feeds (ticker, order book (L2), and trade streams) are available without a Kraken account."* Coinbase was chosen for the `matches` channel's `trade_id`, a per-`product_id` transaction identifier. `sequence`, by contrast, is shared across all message types Coinbase sends on a connection (heartbeats, `l2update`, `matches`, etc.), so it advances on every message type, not just trades — using it for gap detection on the `matches` channel alone would report a "gap" on every non-match message, firing constantly and telling us nothing real.
Breaks if: Coinbase's own docs are explicit that *messages can be dropped from the matches channel* and recommend cross-checking against the `heartbeat` channel's `last_trade_id` (or REST) to detect misses — `trade_id` gap-logging from the `matches` channel alone can under-detect drops the channel itself doesn't deliver. Since backfill is out of scope, this is acceptable (log what the gap in `trade_id` reveals, move on) but worth revisiting at Stage 2: subscribing to `heartbeat` alongside `matches` is a cheap, independent second source for the same check.

## Node Kafka client: `@confluentinc/kafka-javascript`, not KafkaJS

Chose: `@confluentinc/kafka-javascript` (Confluent's GA client, built on librdkafka).
Over: KafkaJS.
Because: KafkaJS has had no release since February 2023, and Kafka 4.0 removed several old client protocol API versions (KIP-896: Produce V0–V2, Fetch V0–V3, ListOffset V0, OffsetCommit V0–V1 — the last explicitly called out as affecting KafkaJS). This isn't theoretical: [tulios/kafkajs#1752](https://github.com/tulios/kafkajs/issues/1752) reports KafkaJS consumers failing to join a consumer group against Kafka 4.0.0 in KRaft mode with "the group coordinator is not available," with no fix available since the project is unmaintained. `@confluentinc/kafka-javascript` is the actively maintained, vendor-supported replacement CLAUDE.md flagged for evaluation.
Breaks if: Confluent's client has a materially different config surface than KafkaJS (it does — it's not a drop-in), so ingester code should target this client's API directly rather than write against a KafkaJS-shaped abstraction "just in case."

## Kafka healthcheck: `/opt/kafka/bin/kafka-broker-api-versions.sh`, not curl

Chose: `/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092` (full path) as the Compose healthcheck command for the `kafka` service.
Over: a `curl`-based HTTP check; the bare script name without its path.
Because: `apache/kafka:4.3.1` is not built on an image that includes `curl` or `nc`. It does ship the full Kafka distribution's scripts, but under `/opt/kafka/bin/`, which is **not** on `PATH` (`PATH` inside the image is `/opt/java/openjdk/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` — checked directly with `docker run --entrypoint sh apache/kafka:4.3.1 -c 'which kafka-broker-api-versions.sh'`, which fails). The script itself does a real protocol-level round trip (an ApiVersionsRequest) rather than a bare TCP connect, so a healthy result actually means the broker is answering Kafka's protocol, not just that the port is open.
Breaks if: the script's location or output format changes across major versions — worth re-checking the path on any future Kafka version bump. Verified: `docker compose exec kafka /opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092` exits 0 and prints the broker's supported API version ranges against the running compose stack; `docker compose up` independently reports the `kafka` container reaching `healthy` using this same command.

## Internal topic replication factor: 1, set explicitly

Chose: `offsets.topic.replication.factor=1`, `transaction.state.log.replication.factor=1`, `transaction.state.log.min.isr=1` on the broker.
Over: leaving these at their broker defaults (3, 3, 2 respectively).
Because: Kafka's internal topics (`__consumer_offsets`, and `__transaction_state` if a transactional producer is ever used) are created with these replication factors the first time they're needed — for `__consumer_offsets`, that's the first consumer group offset commit, i.e. Stage 3. With one broker, a default of 3 makes that internal topic creation fail outright (not enough brokers to satisfy the replica count), which would surface as a confusing consumer-side error in Stage 3 with nothing wrong in the code. This follows directly from the project's own single-broker/RF=1 decision (stated in CLAUDE.md's stack section) — it just applies it to Kafka's internal topics too, not only `ticks`.
Breaks if: a second broker is ever added — these internal topics would still be stuck at RF=1 unless explicitly reconfigured with `kafka-reassign-partitions` or similar; out of scope per "multi-broker Kafka" being excluded from this project.

## Compose file structure: no ports in the base file

Chose: `compose.yaml` (base, shared by dev and prod, no `ports:` published anywhere) + `compose.override.yaml` (dev-only, loaded automatically by `docker compose up` with no `-f` flags, adds host port publishing) + `compose.prod.yaml` (prod override, applied explicitly as `docker compose -f compose.yaml -f compose.prod.yaml up`).
Over: publishing dev ports directly in `compose.yaml` and having `compose.prod.yaml` attempt to remove them.
Because: Compose merges `ports:` lists across files — it has no mechanism for one file to *remove* a port another file published. If dev ports lived in the base file, `compose.prod.yaml` could add to them but never strip them, making it structurally impossible to keep Kafka/Redis off the public internet in prod (invariant #10) while using the same base file. Putting dev's ports in the auto-loaded override instead means the base file is inherently port-free, and prod (which never loads the override) simply never has ports to strip in the first place. Dev ports are further bound to `127.0.0.1` specifically (`127.0.0.1:29092:29092`, `127.0.0.1:6379:6379`), not just published — so even on the dev machine nothing on the LAN can reach them.
Breaks if: someone runs `docker compose -f compose.yaml -f compose.override.yaml -f compose.prod.yaml up` by hand — mixing all three would republish dev's ports on top of prod. Prod must be brought up with exactly `-f compose.yaml -f compose.prod.yaml`, never including the override.

## Redis image and data volume

Chose: `redis:8.2.9-alpine`, pinned to the exact patch version, with a named volume (`redis-data`) mounted at `/data` (the image's default `dir`).
Over: an unpinned or minor-pinned tag (`redis:8.2-alpine`, `redis:alpine`); an anonymous volume.
Because: `redis:8.2-alpine` and `redis:8.2.9-alpine` currently resolve to the identical image (same digest, confirmed by pulling both), but only the patch-pinned tag stays reproducible if `8.2.10` etc. is released later — consistent with the same pin-everything reasoning applied to Kafka. A named volume is needed for the same reason as Kafka's: an anonymous volume can be orphaned by container recreation, silently losing the AOF file and defeating the whole point of `--appendonly yes`.
Breaks if: nothing specific; re-pin when intentionally upgrading Redis. Verified: `docker run --rm redis:8.2.9-alpine redis-server --version` reports `v=8.2.9`; `redis-cli CONFIG GET appendonly` returns `yes` and `/data/appendonlydir` exists after `docker compose up`.

## Ingester Node.js version: `engines` range `>=24 <25`, exact `24.21.0` pinned via `.nvmrc`

Chose: `package.json` declares `"engines": { "node": ">=24 <25" }` (accepts any Node 24.x, rejects 23 or 26); `.nvmrc` pins the exact patch, `24.21.0`, for local version managers (`fnm`/`nvm`) to install and switch to.
Over: pinning the exact `24.21.0` in `engines` too; pinning to `26.8.2`, the version actually installed on this machine before this decision (`node --version` → `v26.8.2`, via Homebrew).
Because: CLAUDE.md specifies "current Node.js LTS" for the ingester — as of today Node 24 is Active LTS and Node 26 is still Current (becomes LTS 2026-10-28), so 24.x is the correct line. `engines` is an npm-enforced compatibility check across whoever/whatever runs this package (CI later, a teammate, a future you) — an exact-version `engines` pin is needlessly strict for that purpose and would reject a routine 24.21.1 patch release for no reason; the range expresses "must be on the LTS-24 line" without pinning a moment in time. `.nvmrc`, by contrast, exists specifically to pin an exact, reproducible version for local dev tooling to install — that's where the exact patch belongs.
Breaks if: development on this machine runs on the globally-installed 26.8.2 day to day while these files declare 24.x — installing 24.21.0 via `fnm` and confirming `node --version` before `npm install` avoids `@confluentinc/kafka-javascript`'s native module build happening against the wrong Node ABI. This isn't hypothetical: see the `engine-strict` decision below.

## `ingester/.npmrc`: `engine-strict=true`

Chose: `engine-strict=true` in `ingester/.npmrc`, making the `engines` range in `package.json` a hard install-time gate instead of an advisory.
Over: leaving `engines` as documentation only (npm's default behavior — it warns, but installs anyway).
Because: this already happened once. Writing this code, the shell running `npm install` didn't have `fnm`'s environment sourced (a fresh non-interactive shell that predated adding `fnm` to `.zshrc`), so `which node` silently resolved to Homebrew's `v26.8.2` instead of the pinned `24.21.0` — `npm install` proceeded without complaint and compiled `@confluentinc/kafka-javascript`'s native addon against the wrong Node ABI. It was caught only by checking `node --version` immediately before the install and noticing the mismatch, then killing the running install and rebuilding from a clean `node_modules`. `engine-strict` turns that class of mistake into a loud `EBADENGINE` failure at `npm install` time instead of a silently-wrong native build discovered later (or not discovered at all, if it happened to work) — confirmed by re-running `npm install` under Homebrew's `v26.8.2`: it now refuses immediately (`Required: {"node":">=24 <25"} / Actual: {"node":"v26.8.2"}`) instead of installing.
Breaks if: someone needs to install with a Node version outside the declared range for a one-off reason — `engine-strict` has no per-command override short of editing `.npmrc` or passing `--engine-strict=false`, which is the point: it should be inconvenient to bypass, not silently skipped.

## Ingester language: TypeScript, not plain JavaScript — plus a hand-written runtime guard for WebSocket data

Chose: TypeScript, run directly in dev via `tsx` (no separate compile step during development). **Correction to an earlier version of this entry:** TypeScript only checks code that flows through statically-typed values — it catches us mismapping our own fields when *constructing* the outgoing Kafka message (e.g. writing `exchangeTs` as a string, or transposing two fields), because that code is ours and fully typed. It does **not** validate the data actually arriving over the Coinbase WebSocket: `JSON.parse()` of a network message returns `any`/`unknown`, and nothing stops us from asserting a type onto it that the real payload doesn't match — Coinbase sending a malformed or unexpected message wouldn't be caught by the type system at all, it would just be silently mis-cast.
Over: plain JavaScript (no build-time checking on our own code either); reaching for a validation library (`zod`, `ajv`, etc.) for the runtime side.
Because: TypeScript still earns its place for the code we write (the message-construction path, the config loader) — schema v1 is a contract other services depend on, and a typo'd key or wrong-typed field in *our own* code is worth catching at edit time. But the WebSocket boundary needs an explicit, hand-written runtime check, not type annotations: a small type guard function (`isMatchMessage(msg: unknown): msg is CoinbaseMatchMessage`) that checks `typeof price === 'string'`, `typeof size === 'string'`, `typeof trade_id === 'number'`, `!Number.isNaN(Date.parse(time))`, and `configuredSymbols.includes(product_id)`. Anything that fails is logged and dropped, not produced to Kafka. A validation library is unnecessary weight for one message shape with five fields to check — hand-written conditionals are shorter than the equivalent schema definition and just as clear.
Breaks if: the guard's checks and the `CoinbaseMatchMessage` type ever drift apart (someone changes the type without updating the guard, or vice versa) — the guard is the actual boundary enforcement, the type is documentation for code past that boundary. `tsx` remains a dev-time convenience; whether the eventual Dockerfile runs compiled `dist/*.js` or `tsx` directly against `src/` is a Stage-9-adjacent decision, not one to make now.

## Ingester dev run mode: host via `npm`, not containerized yet

Chose: run the ingester directly on the host during Stages 1–2 (`npm run dev`, connecting to Kafka at `127.0.0.1:29092`, the `EXTERNAL` listener), no Dockerfile yet.
Over: containerizing the ingester now and running it against `kafka:9092` (the `INTERNAL` listener) from the start, for parity with how it'll run in prod.
Because: `@confluentinc/kafka-javascript` is a native module — containerizing now means every code change costs an image rebuild (or a bind-mount + reinstall-in-container dance) for zero benefit while the code is still this small and single-instance. The `EXTERNAL` listener exists specifically for this case (see the listener topology decision above). Containerizing is cheap to add later and doesn't need deciding now — consistent with implementing one component at a time rather than scaffolding ahead of the current stage.
Breaks if: this is revisited once the ingester needs to run unattended (Stage 9/10) or needs to join `compose.yaml` so `docker compose up` brings up the whole pipeline in one command — at that point it gets a Dockerfile and switches to `kafka:9092`.

## Stage 1 tick message: full schema v1 now, `trade_id` mapped to `exchangeSeq`

Chose: produce the full schema v1 shape from Stage 1 (`{ v: 1, symbol, price, size, exchangeTs, ingestTs, exchangeSeq }`), not a stripped-down interim shape.
Over: a minimal ad hoc shape for Stage 1 (e.g. just `{ symbol, price }`) and expanding to full schema v1 in Stage 2.
Because: schema v1's fields are already fully specified in this file's data contracts, and the `exchangeSeq` field's source (`trade_id`, not `sequence`) is already decided. There's nothing left to design at Stage 2 that would change the shape — Stage 2 adds *behavior* (idempotent producer config, reconnect, gap logging using the `exchangeSeq` field this stage already writes), not new fields. Writing the real shape now avoids a schema migration for a field set that's already settled.
Field mapping from Coinbase's `match` message (verified shape: `{type, trade_id, maker_order_id, taker_order_id, side, size, price, product_id, sequence, time}`, `trade_id`/`sequence` as JSON numbers, `price`/`size` as strings, `time` as an ISO 8601 string):
- `symbol` ← `product_id` (already in our `SYMBOLS` format, e.g. `"BTC-USD"` — no translation needed)
- `price` ← `price` (already a string — pass through, no parsing)
- `size` ← `size` (already a string — pass through)
- `exchangeTs` ← `Date.parse(time)` (ISO 8601 → epoch ms; Coinbase's microsecond precision is truncated to ms, which is what our field is)
- `ingestTs` ← `Date.now()` at the point the ingester constructs the record
- `exchangeSeq` ← `trade_id` (per the earlier exchange decision — not `sequence`)
Breaks if: Coinbase ever changes `matches` channel field names or types without a version bump on their side (nothing to do differently now — this is the same risk any integration with an external feed carries, not something Stage 1 needs to guard against).

## WebSocket client: `ws`, not Node's built-in global `WebSocket`

Chose: the `ws` npm package.
Over: Node's built-in global `WebSocket` (available since Node 21, backed by `undici`).
Because: the built-in `WebSocket` deliberately implements the WHATWG browser spec, which never exposes control frames to application code — no `.ping()` method, no `'ping'`/`'pong'` events; the browser (and Node's spec-compliant implementation of it) handles those transparently below the API surface script can reach. `ws` is a Node-native implementation that exposes ping/pong directly (`socket.ping()`, `socket.on('pong', ...)`). Stage 2's stale-connection detection is likely to want exactly that: sending an application-level ping on an interval and treating a missing pong as the "no message for N seconds" signal, rather than only inferring staleness from the absence of data messages (which `matches` won't send at all if a symbol is simply quiet — not the same thing as a dead connection).
Breaks if: nothing yet — this is a Stage 1 dependency choice made now because it's the kind of thing that's annoying to swap later, not because Stage 1 itself uses ping/pong (it doesn't; that's Stage 2).

## Stage 2 note (not solved now): `ws` ping/pong and Coinbase's `heartbeat` channel are complementary, not redundant

Chose: not deciding the stale-connection design yet — recording that Stage 2 likely wants both mechanisms, for different failure modes.
Because: `ws`'s ping/pong proves the TCP/TLS socket itself is alive — the transport is up and Coinbase's server is responding to frames at all. It says nothing about whether the *feed* is alive per product: a socket can be perfectly healthy while a specific product's `matches` channel goes quiet because Coinbase stopped sending for that product_id (the exact "bad `product_id`" silent-failure shape already handled by logging `error`/`subscriptions` — see above — but also relevant to an established connection). Coinbase's `heartbeat` channel, subscribed per product, proves the feed is alive per product and — already noted above — carries `last_trade_id`, which Stage 2 also wants as the gap-detection baseline. So the two mechanisms answer different questions: "is the socket up" (ping/pong) vs. "is this product's data still flowing, and what's the last trade_id I should expect continuity from" (heartbeat).
Breaks if: this is not designed yet — deferred to Stage 2 by explicit instruction. Recorded now so Stage 2 doesn't have to rediscover that one mechanism doesn't substitute for the other.
## Coinbase message types: handle `match`, `subscriptions`, and `error` explicitly; skip `last_match` deliberately

Chose: an explicit switch on the WebSocket message's `type` field — produce to Kafka only for `type === "match"`; log the `subscriptions` confirmation at info level once, right after connecting; log `error` messages loudly (not swallowed); explicitly recognize and skip `last_match` (Coinbase sends one per product immediately after subscribing, containing the most recent trade from before the subscription); log a warning and drop anything else unrecognized.
Over: only handling `match` and ignoring everything else silently.
Because: a bad `product_id` (typo in `SYMBOLS`, or a delisted/renamed pair) doesn't error the WebSocket connection — Coinbase just never sends `match` messages for it, which looks identical to "market is quiet" from the ingester's point of view. Without logging `error` messages loudly and confirming `subscriptions`, that failure mode is silent: the vertical slice "works" (connects, stays open) while producing nothing, and the "Done when" `kcat` check would just show an empty topic with no clue why.
Breaks if: nothing now — `last_match` is skipped, not produced, but it's not thrown away conceptually: its `trade_id` is the natural baseline for Stage 2's gap detection (the first real `match` after subscribing should be compared against `last_match`'s `trade_id`, not treated as if there's no prior state at all). Recorded here so Stage 2 doesn't have to rediscover this message exists.

## Coinbase subscription scope: the full configured `SYMBOLS` list, not a first-symbol special case

Chose: `config.ts` reads all of `SYMBOLS` and subscribes to the full list in one `product_ids` array.
Over: subscribing only to the first configured symbol as a Stage-1-specific simplification.
Because: `product_ids` already accepts an array — there's no per-symbol subscription call to fan out, so handling the full list costs nothing extra in code. Special-casing "just the first one" would be an artificial restriction that adds a code path (and a TODO) purely to look more like a "vertical slice," when the real vertical-slice scope reduction is behavioral (no reconnect, no idempotence config, no gap logging — Stage 2's job), not about how many symbols are subscribed. Dev's `.env` sets `SYMBOLS=BTC-USD` for Stage 1, so in practice exactly one symbol flows regardless — but the code path handles N from the start, consistent with invariant #8.
Breaks if: nothing — this removes a special case rather than adding one.

Chose: `node --env-file=.env` (via the `dev` npm script), no `dotenv` dependency.
Over: `dotenv`.

Breaks if: not verified yet — this is a Stage 1 note, decided now (while other base-image-adjacent decisions are being made) so it doesn't surprise us mid-stage; confirm `@confluentinc/kafka-javascript` actually installs and runs cleanly on `node:<lts>-slim` before writing the ingester Dockerfile.

## Open question for Stage 3 (not solved now): simultaneous matches from one taker order all get Δt=0

Chose: not addressing this now — recorded so Stage 3's EMA implementation doesn't discover it mid-stage.
Over: designing around it in the ingester or the message schema today (e.g. synthesizing a sub-timestamp tiebreaker, or coalescing same-timestamp matches).
Because: a single taker order that matches against several resting orders produces multiple `match` messages sharing the exact same `time` value (each maker fill is a separate trade with its own `trade_id`, but Coinbase timestamps the whole taker order's fills identically). Stage 3's EMA update takes `Δt` from `exchangeTs`, and `alpha = 1 - exp(-Δt/τ)`. When `Δt = 0`, `alpha = 0`, so the EMA update is a no-op — the second, third, etc. match at an identical timestamp changes `lastOffset` and gets stored, but has zero effect on the EMA value, even though each is a real, distinct trade at (possibly) a different price. The first match in the group is the only one that actually moves the EMA.
Breaks if: this becomes visible as "the EMA doesn't seem to react to some trades" during Stage 3 verification, especially during volatile bursts where large taker orders sweeping the book are common — worth deciding then whether that's acceptable (arguably it's a defensible reading of "time-decayed" — no time passed, so no decay applies) or whether same-timestamp matches should be coalesced (e.g. volume-weighted average price across the batch) before feeding the EMA. Not a Stage 1/2 concern.

## Stage 2 note (not built now): validate the `subscriptions` confirmation against configured symbols; fail-fast vs. retry

Chose: not building this yet — recording the design for Stage 2, prompted by observing the actual failure mode live: subscribing with an invalid product id (`BTC-USDX`) during Half A verification produced a loud `error` message (already logged, per the existing message-type-handling decision), but the ingester kept running afterward with a `subscriptions` confirmation whose `channels[].product_ids` came back empty for that channel — i.e., the process stays up and "healthy" while silently tracking nothing.
Over: treating the `error` message alone as sufficient signal to act on.
Because: `error` tells us Coinbase rejected something, but doesn't by itself tell the ingester whether the thing it now believes it's subscribed to actually matches what it was asked to track. The `subscriptions` confirmation is the authoritative source for that — Stage 2 should diff `subscriptions`'s `product_ids` against the configured `SYMBOLS` list and treat any missing symbol as fatal. This is a **config** error (the deployed configuration doesn't match reality — a typo, a delisted pair) — categorically different from a **network** error (a dropped connection, a timeout), which Stage 2's reconnect/backoff logic should retry through instead of exiting. Conflating the two would either exit on a transient network blip (wrong) or retry forever against a permanently-wrong symbol (also wrong, and silent).
Breaks if: exiting non-zero on a config mismatch needs to interact correctly with whatever supervises the process (Compose `restart` policy, systemd, etc.) once the ingester is containerized — a bare non-zero exit under an unconditional `restart: always` would just crash-loop forever, which is the same silent-failure shape this is meant to fix, just noisier. Worth deciding the ingester's restart policy alongside this in Stage 2, not before.

## Offset commit behavior: Spring Kafka defaults stated explicitly, kept as-is for Stage 1

Chose: keep Spring Kafka's defaults for Stage 1 — do not configure `AckMode` or a custom error handler yet.
Over: configuring manual acknowledgment now, ahead of Stage 3's actual requirement for it.
Because: these defaults need to be on the record precisely, since Stage 3 (invariant #3: commit only after the Redis write succeeds) will replace them, and because one of them is a real message-loss path worth knowing about before it's hit by accident.
- **`enable.auto.commit=false`**: Spring Kafka disables the Kafka client's own periodic auto-commit by default, specifically so the *container* controls when commits happen, rather than a background thread committing on a timer independent of whether the listener actually finished processing.
- **Default `AckMode`: `BATCH`** (`ContainerProperties.AckMode.BATCH`) — per its javadoc, "commit the offsets of all records returned by the previous poll after they all have been processed by the listener." This is a real candidate for satisfying invariant #3, not something Stage 3 must necessarily replace: if each record's Redis write happens synchronously inside the listener before it returns, then by the time the batch's last record has "been processed," every record in it already has a successful Redis write behind it, so nothing is ever committed ahead of its write. What `BATCH` changes is only how much gets replayed after a crash — up to a full poll batch instead of a single record — and that replay is exactly what the offset-CAS in `apply_tick.lua` (invariant #2) is designed to make a safe no-op. `BATCH` would only violate invariant #3 if the Redis write were made asynchronous relative to the listener returning.
- **Default error handling (`DefaultErrorHandler`)**: a listener that throws for a given record is retried with `FixedBackOff(0L, 9)` — the initial attempt plus 9 retries, 0ms apart, 10 total attempts. Once exhausted, the default recoverer logs the record at ERROR and treats it as handled. Combined with `AckMode.BATCH`, this means **the container commits straight past a record that permanently fails to process** — a real, silent message-loss path, not a hypothetical one.
Breaks if: this is hit before Stage 3 addresses it — e.g. a malformed JSON value or a missing `price` field would retry ten times near-instantly, log an error, and then be gone forever with no trace beyond that one log line. Acceptable for Stage 1's "log symbol/partition/offset/price, nothing else" scope; Stage 3 must decide deliberately whether skip-and-log is still acceptable once actual state (EMA, alerts) is on the line, or whether a dead-letter topic is needed. `AckMode.BATCH` itself is not the thing in question here — per the correction above, it remains a valid candidate as long as the Redis write stays synchronous in the listener. What Stage 3 actually decides is the *error-handling* policy: what happens to a record that keeps throwing after retries are exhausted, independent of which `AckMode` is in use.

## `auto.offset.reset=earliest` — a permanent choice, not a Stage 1 convenience

Chose: `spring.kafka.consumer.auto-offset-reset=earliest`.
Over: `latest` (Spring Kafka's default if left unset).
Because: this setting is consulted **only** when Kafka has no committed offset to resume from for this consumer group/partition — a brand-new group (true today: this is the first time `ema-consumers` exists) or an existing group whose committed offset expired (`offsets.retention.minutes` elapsed during a long enough outage). On an ordinary restart with a valid committed offset, this setting isn't consulted at all — the committed offset wins regardless. In the narrow case where it does apply, `latest` jumps straight to new production and silently skips everything produced while there was no valid checkpoint — permanent, invisible data loss with no trace it happened. `earliest` instead replays the whole visible topic, and that replay is safe specifically because of Stage 3's offset-CAS design (`apply_tick.lua` only applies a tick if its offset is greater than the stored `lastOffset`, invariant #2): re-delivering ticks already reflected in Redis state is a guaranteed no-op, not reprocessing risk. So `earliest` costs replay time in the rare case it triggers; `latest` costs silent permanent loss in that same case. That asymmetry makes `earliest` the correct general-purpose choice for this project, not a Stage-1-only convenience to reconsider once rebalancing (Stage 4) is in play.
Breaks if: topic retention or volume ever grows large enough that a full replay becomes genuinely expensive — not a concern at this project's scale (6-hour retention, dev-scale volume).

## `consumer/.sdkmanrc`: pin `java=25.0.4-tem`, backed by `maven-enforcer-plugin`

Chose: a `.sdkmanrc` file in `consumer/` pinning `java=25.0.4-tem`, plus a `maven-enforcer-plugin` execution with `requireJavaVersion` set to `[25,26)`, bound to the `validate` phase so it runs before anything else.
Over: relying on whatever JDK happens to be active in the shell; the `.sdkmanrc` pin alone, without a build-time check.
Because: same motivation as the ingester's `.nvmrc`/`engine-strict` pair — pin the exact toolchain version in the repo itself so `sdk env` (with `sdkman_auto_env=true`) activates the right JDK on `cd`, the same way `fnm`'s `--use-on-cd` does for Node. But `.sdkmanrc` alone is an honor-system pin: nothing stops `./mvnw` from running under whatever JDK happens to be on `PATH` if `sdk env` wasn't actually run first — unlike `engine-strict`, which npm enforces at install/run time regardless of what a human did or didn't do first. The enforcer rule closes exactly that gap: the build fails immediately, with a clear message, under any JDK outside `[25,26)`, instead of silently compiling and possibly succeeding under a JDK Spring Boot 4.1.1 wasn't verified against.
Breaks if: the project ever needs to move off Temurin 25 (e.g. a future LTS) — the version range must be bumped in `pom.xml` at the same time as `.sdkmanrc`, or the enforcer rule will reject the very JDK the project is trying to move to.

## Consumer JSON handling: Jackson 3 (`tools.jackson`) via `spring-boot-jackson`, not a bare `jackson-databind` dependency

Chose: `org.springframework.boot:spring-boot-jackson` (Boot-managed at `4.1.1`) as the consumer's only JSON dependency, for the one piece of JSON parsing Stage 1 needs (pulling `price` out of the tick's JSON value).
Over: Jackson 2 (`com.fasterxml.jackson.core:jackson-databind`), which Spring Boot 4.1.1 still manages separately (`jackson-2-bom` at `2.21.5`) via an opt-in `spring-boot-jackson2` compatibility starter for applications migrating from Boot 3; also over depending directly on `tools.jackson.core:jackson-databind` (Jackson 3, Boot-managed at `3.1.5`).
Because: Spring Boot 4's own default JSON stack is Jackson 3 — confirmed directly against Maven Central: `jackson-databind:3.1.5`'s actual groupId is `tools.jackson.core`, not `com.fasterxml.jackson.core`. Reaching for Jackson 2 here would mean depending on Boot's legacy-compatibility path in brand-new code, and the import is `tools.jackson.databind.ObjectMapper`, not `com.fasterxml.jackson.databind.ObjectMapper` — worth stating plainly since essentially every Jackson tutorial and Stack Overflow answer in existence still shows the Jackson 2 package. But a bare `tools.jackson.core:jackson-databind` dependency was tried first and is wrong: it puts the library on the classpath without Boot's autoconfiguration, so there is no `ObjectMapper` bean to inject — confirmed directly by inspecting the resolved jars: `spring-boot-autoconfigure-4.1.1.jar` (pulled in by `spring-boot-starter`) has no Jackson classes at all, and `JacksonAutoConfiguration` only turned up once `spring-boot-jackson-4.1.1.jar` was on the classpath (verified with a throwaway probe POM depending on `spring-boot-starter-json`, whose dependency tree resolves `spring-boot-jackson`, and unzipping it directly to confirm the class is inside). Spring Boot 4 moved per-feature autoconfiguration out of the monolithic `spring-boot-autoconfigure` into smaller feature modules; Jackson's now lives in `spring-boot-jackson`, a compile-scope dependency (no web starter needed) that pulls in `tools.jackson.core:jackson-databind` transitively along with the autoconfiguration.
Breaks if: a future Spring Boot version reorganizes autoconfiguration modules again — re-check with the same throwaway-probe-plus-unzip method rather than assuming a given starter still carries the autoconfiguration it does today.

## Structured logging: Boot's built-in `logging.structured.format.console=ecs`, no extra dependency

Chose: `logging.structured.format.console: ecs` in `application.yml`, and SLF4J 2's fluent API (`log.atInfo().addKeyValue(...).log(...)`) in `TickConsumer` to attach `symbol`, `partition`, `offset`, `price` as structured fields on each log line.
Over: `logstash-logback-encoder` (a third-party Logback encoder, the most common way to get JSON logs pre-Boot-3.4) and hand-rolled JSON via `String.format`.
Because: Spring Boot 3.4+ (so 4.1.1 too) ships structured logging support built into `spring-boot-starter-logging`, already on the classpath — setting one property is enough to get JSON console output, no added dependency to track a version for. `logstash-logback-encoder` would add a dependency to do something Boot's own starter already does. The `ecs` format (over `logstash` or `gelf`, the other two built-in options) was picked because it's a documented, versioned schema (Elastic Common Schema) rather than a shape implicitly defined by whatever a log aggregator happens to expect; any of the three would have satisfied the code-conventions requirement ("every consumer log line about a record includes `symbol`, `partition`, `offset`") equally well, since that requirement is about which fields are present, not which JSON shape wraps them. `addKeyValue()` (not string-interpolating the fields into the log message) is what makes those fields appear as separate structured fields in the output rather than being buried inside the message text.
Breaks if: nothing yet. If Sentry (Stage 9) or a log aggregator later expects a specific shape, that's a reason to reconsider `ecs` specifically — not a reason to reconsider Boot's built-in structured logging over `logstash-logback-encoder`, since Boot's structured logging also supports a fully custom format via a user-supplied `StructuredLogFormatter` if none of the three built-ins fit.

## Incident: consumer compiled but never ran — same Boot-4-modularization mistake as Jackson, this time on Kafka

Chose: `org.springframework.boot:spring-boot-starter-kafka` in place of a direct `org.springframework.kafka:spring-kafka` dependency.
Over: the original `spring-kafka` dependency, which compiled without error and produced a `BUILD SUCCESS`, but `./mvnw spring-boot:run` exited in ~0.3s with no Kafka client logs and no listener ever starting.
Because: the failure was the exact same shape as the Jackson mistake above, just undetected until actually run instead of caught at compile time — depending on the raw third-party library (`org.springframework.kafka:spring-kafka`) puts `@KafkaListener` support's *runtime dependency* on the classpath, but not Boot's autoconfiguration that actually registers a listener container for it. Verified the same way as Jackson, not assumed: a throwaway probe POM depending on `spring-boot-starter-kafka` resolves `org.springframework.boot:spring-boot-kafka:4.1.1` transitively, and unzipping that jar directly shows `org.springframework.boot.kafka.autoconfigure.KafkaAutoConfiguration` inside it — absent from the classpath before this fix. Without it, no `ConcurrentKafkaListenerContainerFactory` bean exists, `@KafkaListener` is never processed, no listener thread starts, and a Spring Boot application with no non-daemon threads left to keep it alive exits cleanly right after context startup — hence `BUILD SUCCESS` with nothing having actually run. After the fix, ran the consumer against the live Compose stack (with the ingester also running, host-run via `npm run dev`) and confirmed directly: the process stayed up, `ConsumerConfig values` logged `group.id = ema-consumers`, `auto.offset.reset = earliest`, `enable.auto.commit = false`, and `TickConsumer` logged hundreds of `tick received` lines with `symbol`, `partition`, `offset`, `price` as separate structured fields, matching live ticks from the ingester's own log.
Breaks if: this class of mistake recurs for any future Boot 4 dependency — **compiling is not running**. A Spring Boot module that provides autoconfiguration conditionally on a library being present is not the same thing as depending on that library directly, and Boot 4's modularization means the autoconfiguration for a given library increasingly lives in its own `spring-boot-<feature>` jar, reachable only via `spring-boot-starter-<feature>`. A clean compile proves the code is well-typed against whatever's on the classpath; it proves nothing about which Spring beans actually get created at runtime. The check that catches this is running the application and confirming the specific behavior expected (a listener thread, a config log, and so on) — not just a successful build.

# Stage 2 — Ingester hardening

Stage 2 stays host-run, same as Stage 1 (`npm run dev`, `--env-file`). Containerizing the ingester and choosing its Compose restart policy are Stage 9 work, not Stage 2 — decided explicitly rather than left implicit, because the exit-code split below only matters once something is watching the process and deciding whether to restart it, and nothing is yet.

## Exit codes: `78` (`EX_CONFIG`) for a configuration error, `1` for any other fatal error

Chose: `process.exit(78)` specifically for the subscriptions/config-mismatch case (see below), `process.exit(1)` for every other fatal path this stage adds (unrecoverable produce failure, producer queue full) and for the pre-existing top-level crash handler.
Over: `process.exit(1)` for everything, undifferentiated.
Because: `78` is `EX_CONFIG` from BSD `sysexits.h` — a long-standing, if informal, convention for "the program's configuration is wrong, don't just retry it as-is." Splitting it out now costs nothing (it's one literal) and means a future restart policy (Stage 9) can tell "this will never succeed without a human changing `SYMBOLS`" apart from "this failed for a possibly-transient reason, a restart might help" — exactly the distinction the fail-fast-vs-retry design below depends on being externally visible, not just internally reasoned about.
Breaks if: nothing yet — recorded now so Stage 9's restart policy is designed against a real, already-shipped exit-code contract instead of having to go back and add one.

## Idempotent producer: `idempotent: true`, `acks: -1`, `maxInFlightRequests: 5`, `retries` raised off the client's own default

Chose: `idempotent: true`, `acks: -1`, `maxInFlightRequests: 5`, `retries: 2147483647` (`Number.MAX_SAFE_INTEGER`-scale, but capped to librdkafka's actual `int32` config range) in the producer config.
Over: leaving `retries` at whatever the client defaults to; using the string `'all'` for `acks`.
Because: verified against the installed client's source (`node_modules/@confluentinc/kafka-javascript@1.10.1/lib/kafkajs/_producer.js`), not assumed:
- `idempotent: true` is a KafkaJS-shaped config key this client translates to the real `enable.idempotence` librdkafka setting (`if (Object.hasOwn(kjsConfig, 'idempotent')) rdKafkaConfig['enable.idempotence'] = kjsConfig.idempotent;`).
- `acks` is passed straight through as `rdKafkaConfig['acks']`, and this client's own compatibility-error text (`createReplacementErrorMessage(..., 'acks: <number>', ...)`) confirms it wants a **number**, not the KafkaJS string `'all'` — so `-1`, librdkafka's numeric spelling of "all in-sync replicas," not `'all'`.
- `retries` is *not* passed through with librdkafka's own generous default (`message.send.max.retries`, native default `2147483647`, confirmed in `deps/librdkafka/CONFIGURATION.md`). This JS layer overrides it: `rdKafkaConfig["retries"] = retries ?? 5`. Left unset, the effective retry budget here is 5, not "effectively unlimited" — worth stating explicitly since it would have been a reasonable but wrong assumption that the native default applies.
- `maxInFlightRequests: 5` is set explicitly (→ `max.in.flight`) because Kafka's idempotence protocol caps in-flight requests per connection at 5; rather than rely on undocumented auto-clamping behavior, the limit is stated in code.
What idempotence guarantees here: per-partition sequence numbers let the broker detect and drop duplicate or reordered deliveries caused by a *producer retry* — a message that librdkafka resent because it didn't get an ack in time, not because the application sent it twice. Since every symbol maps to exactly one partition for its whole life (invariant #1), this is ordering/no-duplication per symbol, which is everything this project needs from it. It does not cover the same-trade-produced-as-two-different-records case below (that's the trade_id watermark, a different mechanism for a different failure). `acks=-1` is required by Kafka to enable idempotence at all — with RF=1 this isn't buying extra replication durability over `acks=1` (there's only one replica either way), it's satisfying a protocol precondition.
Breaks if: nothing yet.

## Final delivery failure and producer-queue-full: log and exit `1`, don't skip-and-continue

Chose: `message.timeout.ms: 30000` (30s) on the producer config, and treat **any** rejection of a `producer.send()` promise — whether from the delivery timeout finally expiring after retries, or from the local queue being full (`ERR__QUEUE_FULL`, immediate rejection, confirmed by tracing `send()` in `_producer.js`: `this.#internalClient.produce(...)` is called synchronously inside a `try/catch` that rejects the message's promise directly on a synchronous throw) — as fatal: log the tick's full context and the error, then shut down and `process.exit(1)`.
Over: the Stage 1 behavior (log the error, drop the tick, keep running).
Because: retries are bounded by `message.timeout.ms` regardless of the `retries` count above — per librdkafka's own docs, "this is the maximum time librdkafka may use to deliver a message (including retries); delivery error occurs when either the retry count or the message timeout are exceeded." An unlimited retry count doesn't mean unlimited time; 30s (well under the library's own 300000ms/5min default) was chosen because this is a live feed feeding a real-time EMA — a tick that took 5 minutes to fail isn't worth much even if it *had* succeeded, and 30s is generous room for a genuine transient broker hiccup without leaving the ingester silently degraded for minutes. If a send is still rejected after that, continuing would mean the WebSocket side (gap detection, watermark) has evidence a trade happened, but Kafka never got it — a hole that no gap-detection mechanism here can see, because gap detection is entirely Coinbase-side (`trade_id` continuity), not Kafka-side. Given backfill is out of scope, that hole is permanent and invisible unless the process stops instead of pretending it's still working. Queue-full is handled identically for the same reason, though at this project's throughput (single digits to low tens of trades/sec even at prod's 10–20 symbols) it's expected to essentially never be the one that actually fires — `queue.buffering.max.messages` defaults to 100000, which `message.timeout.ms: 30000` will almost always trip long before the queue physically fills during an outage. Not tuning the queue limits down to fail faster on queue-full specifically, since the timeout already bounds staleness tightly enough.
Breaks if: 30s turns out too aggressive against real-world Kafka restart/rebalance latency once this runs unattended (Stage 9) and produces spurious exits — revisit the number then, with actual observed restart timings, not now.

## Duplicate suppression: a per-symbol "highest trade_id produced" watermark, separate from the gap-detection baseline

Chose: a second per-symbol map, `highestProducedTradeId`, updated only when a trade is actually handed to `producer.send()`, checked before producing: if an incoming `match`'s `trade_id` is not strictly greater than the stored watermark for that symbol, log it as a duplicate and drop it without producing.
Over: relying on `lastTradeId` (the gap-detection baseline) to also catch duplicates; relying on Stage 3's offset-CAS to catch this instead.
Because: these two maps answer different questions and must not be merged. `lastTradeId` answers "what `trade_id` do I expect next from Coinbase," and is deliberately reset from `last_match` on every reconnect (see below) so a gap can be measured against a fresh baseline. `highestProducedTradeId` answers "have I already sent this exact trade to Kafka," and must **never** reset — resetting it on reconnect would let an actual duplicate through right at the reconnect boundary, which is precisely when Coinbase's `last_match`/`match` sequencing around a resubscribe is least certain. And Stage 3's offset-CAS in `apply_tick.lua` (invariant #2) does not cover this at all: it dedupes *redelivery of the same Kafka record* (a consumer re-reading an offset it already applied). If the same trade gets produced twice, it becomes **two different Kafka records at two different offsets** — the second offset is still greater than the first, so the CAS does not skip it; it gets applied to the EMA a second time as if it were a second, distinct trade. The watermark exists to stop that duplicate from ever becoming a second Kafka record in the first place, upstream of anything Stage 3 can do about it.
Breaks if: nothing yet.

## Stale-connection detection: `ws` ping/pong for a dead transport, the `heartbeat` channel for a dead feed

Chose: both mechanisms, wired to the same recovery path (see "single reconnect path" below):
- `ws.ping()` on an interval, with a shorter pong-timeout; a missed pong calls `ws.terminate()`.
- Subscribing to Coinbase's `heartbeat` channel (confirmed field shape directly from Coinbase's docs — `{ type: "heartbeat", sequence, last_trade_id, product_id, time }`, one message per subscribed product per second) alongside `matches`; if no `heartbeat` arrives for a given product within a threshold, `ws.terminate()`.
Over: inferring staleness only from "no `matches` message for N seconds," the literal wording in this file's build order.
Because: these catch different failures. Ping/pong proves the TCP/TLS socket itself is alive — the transport is up and Coinbase's server answers control frames. It says nothing about whether a specific product's feed is still flowing over that live socket. `heartbeat` proves the opposite: a specific product's feed is alive, on a fixed one-per-second cadence *regardless of trade volume* — which is exactly why it, not `matches` volume, is the right liveness signal. A real, low-volume symbol (expected at prod's 10–20-symbol scale) can go quiet for longer than any reasonable staleness window without anything being wrong; `heartbeat` doesn't go quiet just because the market did.
Breaks if: nothing yet.

## Full reconnect is the one recovery path, not a targeted per-product resubscribe — corrected rationale

Chose: on any trigger (dead socket, `heartbeat` staleness, an ordinary `close`/`error` event), tear down and fully reconnect + resubscribe every configured symbol, funneled through a single `close` handler that decides whether to schedule a reconnect.
Over: resubscribing only the affected product's channels on the existing connection.
Because: **correction of an earlier, wrong claim in this session** — Coinbase's WebSocket does accept `subscribe`/`unsubscribe` on an already-open connection (confirmed directly against Coinbase's docs: repeated `"type": "subscribe"` examples sent against an active feed); a targeted resubscribe is not actually unsupported, and the earlier design note claiming otherwise was wrong. The real reason to still reconnect the whole socket: it's one recovery path instead of two, and the `last_match` gap-detection baseline and the `subscriptions`-confirmation config validation both need to reset and re-run **together**, atomically, for every symbol — that's naturally what happens on a fresh connect + subscribe, and is not naturally what happens from an ad hoc mid-session resubscribe of just one product, which would leave that one symbol's baseline freshly reset while every other symbol's baseline stays exactly where it was — a mixed, harder-to-reason-about state for no real benefit, since the failure modes being recovered from (a dead transport; one product gone quiet) are rare enough that reconnecting everything is cheap.
Breaks if: reconnect frequency ever becomes high enough that resubscribing all symbols on every recovery (vs. just the affected one) has a real cost — not expected at this project's scale (3–20 symbols).
Reconnect funnel: only the `close` event schedules the next attempt (via full-jitter backoff, reset to attempt 0 on a confirmed-good `subscriptions` after reconnecting). `error` only logs. Every other trigger for a reconnect (ping-timeout, heartbeat-staleness) works by calling `ws.terminate()`, which itself raises `close` asynchronously — so there is exactly one place in the code that decides "should a reconnect be scheduled," instead of that decision being duplicated at every trigger site and risking a double-scheduled reconnect race.

## Gap detection: `last_match` seeds the baseline per reconnect; `heartbeat.last_trade_id` also advances it, to catch drops on quiet symbols

Chose: `lastTradeId` (per symbol) is set from `last_match.trade_id` right after each (re)connect, advanced by every real `match`, **and** advanced by `heartbeat.last_trade_id` whenever a heartbeat reports a higher `trade_id` than expected — logging a gap in that last case too, distinguished in the log as `detectedVia: "heartbeat"` rather than `"match"`.
Over: only ever comparing against real `match` messages.
Because: match-based gap detection can only fire when a *later* `match` arrives to reveal that one was skipped. A symbol that goes quiet immediately after a drop — no further trades at all for a while — would never produce that later match, so the gap would never surface. `heartbeat.last_trade_id` is Coinbase's own record of the most recent trade for that product, ticking once a second independent of whether we ever see a `match` for it; comparing it against our baseline catches exactly the case a purely match-based check structurally cannot.
Breaks if: nothing yet.

## Correction: `last_match` seeding the baseline was silently swallowing outage gaps, not just skipping them

Chose: on every reconnect (not the first connect of a process — see below), compare `last_match.trade_id` against the *previous* `lastTradeId` value **before** overwriting it, logging a gap (`detectedVia: "reconnect"`) if it jumped; then produce the `last_match` trade itself if its `trade_id` is above the duplicate-suppression watermark.
Over: the original design (restated here since it was wrong): reset `lastTradeId` straight to `last_match.trade_id` on reconnect and claim the separate `sinceReconnect` flag on the *next real match* covers the outage window.
Because: it doesn't. If we last saw trade 100 before disconnecting, and `last_match` after reconnecting reports 150, trades 101–150 were missed during the outage — but overwriting `lastTradeId` straight to 150 makes 150 the new expected baseline, so the *next* real match (say, 151) looks perfectly contiguous. `sinceReconnect: true` on that match only says "this is the first match since reconnecting," not "trades were missed" — it doesn't even correctly report a gap size, since there's no gap for it to detect once the baseline is already sitting at 150. Worse, trade 150 itself — `last_match`'s own trade — was never produced at all, deliberately skipped by design (see the Stage 1 message-type-handling decision), so it's not just under-reported, it's a real, permanent hole in Kafka on top of the unreported 101–149 range. Comparing against the baseline *before* overwriting it, and producing `last_match`'s own trade, closes both problems: the true gap size is logged, and the one trade we can still recover (unlike 101–149, which are gone with no backfill) actually reaches Kafka.
On the very first connect of a process (tracked via a `connectCount > 1` check, not the pre-existing `firstMatchSeenSinceConnect`/`reconnectAttempt` state, since both of those already get reset in ways that don't distinguish "brand new process" from "later reconnect"): still just seed `lastTradeId` and skip producing. There is nothing to compare against yet, and — this is the important reason, not just an ordering technicality — this trade may already be sitting in Kafka from before this process restarted; the duplicate-suppression watermark is in-memory only and starts empty on every process start, so producing on a first connect could silently duplicate a trade the previous process instance already produced, with no watermark to catch it.
Breaks if: nothing yet.

## Heartbeat gap detection has a same-second race with the `match` it's about; confirm on a second heartbeat before flagging

Chose: track `pendingHeartbeatGapTradeId`, a **map** of symbol → the specific trade_id suspected as of the *first* sighting (not a plain set of symbols). The first heartbeat that reports `last_trade_id` ahead of our baseline records that value without logging anything. On the *next* heartbeat for that symbol, resolve the stored suspicion first — confirm and log only if the baseline is still behind the *stored* trade_id, using that stored value (not the new heartbeat's) as the gap's upper bound — then independently record the new heartbeat's own `last_trade_id` as a fresh suspicion if it's still ahead.
Over: logging immediately on the first heartbeat that shows a gap; and (a bug caught and fixed within this stage, not a rejected alternative) tracking only *which symbols* are suspected, then re-checking against whatever the second heartbeat's `last_trade_id` happens to be.
Because: `heartbeat` and `matches` are independent channel messages, and Coinbase's heartbeat can report a `last_trade_id` for a trade whose own `match` message is still in flight — flagging on the first sighting would report a gap for a trade that was never actually missed, just not yet delivered. But the first fix attempt re-compared against the *second* heartbeat's `last_trade_id`, not the value that was actually pending — in a busy market (this project's actual dev symbol, BTC-USD, qualifies) a different, higher-numbered trade is essentially always in flight at every heartbeat tick, so the check stays "ahead" indefinitely even after the original suspect trade's `match` has long since arrived, producing a false gap on every second heartbeat. Worse, confirming with the fresh (higher) `last_trade_id` then advanced the baseline past trades that hadn't actually been confirmed missing yet, and when the real `match` for the original (lower) trade_id eventually arrived, its handler's baseline update would move `lastTradeId` *backwards* to that lower value — which is exactly what `advanceLastTradeId()` (see below) is a second, independent guard against, but the root cause was comparing against the wrong number in the first place. Storing the specific suspected trade_id and resolving against *that* fixes it at the source: the confirmed gap is always exactly the range between the baseline and the trade_id that was actually still missing a full heartbeat interval later, and the fresh heartbeat's own (likely higher) value starts its own new suspicion cycle rather than being conflated with the old one.
Every `lastTradeId` update — match, `last_match`/reconnect, and this heartbeat path — now goes through a single `advanceLastTradeId(symbol, tradeId)` helper that only sets the map when the new value is strictly greater than what's stored, so the baseline can never move backwards regardless of which of the three independent paths touches it or in what order they race.
Breaks if: a real gap could theoretically take marginally longer than one heartbeat interval to be confirmed and logged (~1–2s), which is fine for what this is — a diagnostic log, not a recovery mechanism. `pendingHeartbeatGapTradeId` is cleared on every reconnect (`connect()`), since a stale suspicion from a previous connection means nothing once the whole state has just been reseeded from a fresh `last_match`.

## Shutdown: an explicit `stopping` flag, and every timer that could schedule future work gets cleared

Chose: a module-level `stopping` boolean, checked and set at the very top of the SIGTERM/SIGINT handler before anything else runs; the `close` handler's reconnect-scheduling checks it and no-ops if set; the shutdown handler explicitly `clearInterval`s the ping timer and heartbeat-staleness check, `clearTimeout`s any pending pong-timeout and any pending reconnect-backoff timer, then closes the socket.
Over: relying on `process.exit()` to end everything, without explicitly tracking or clearing timers first.
Because: this is exactly what "SIGTERM during a backoff wait" would otherwise break — a pending `setTimeout` scheduled to call `connect()` again doesn't know a shutdown started, and without the `stopping` check plus an explicit `clearTimeout`, it would fire mid-shutdown (or race with it) and open a brand-new WebSocket connection while the process is trying to exit. Explicit tracking turns "don't reconnect after shutdown begins" from an accident of timing into a checked invariant.
Breaks if: nothing yet.

## Fix: `shutdown()` was missing the same re-entrancy guard `terminateFatally()` already had

Chose: `if (stopping) return;` as the very first line of `shutdown()`, before it logs or does anything else — matching the guard `terminateFatally()` already had from when it was first written.
Over: leaving `shutdown()` unguarded (what it shipped with initially in this stage).
Because: `terminateFatally()` (the fatal-produce-failure path) and `shutdown()` (the signal-handler path) both flush and disconnect the same producer and both call `process.exit()`, but only one of them checked `stopping` first. A second SIGTERM arriving before the first finishes flushing, or a SIGTERM arriving while `terminateFatally()` is already mid-flush from an unrelated produce failure, would run two overlapping `flush()`/`disconnect()`/`exit()` sequences on the same producer concurrently — at best redundant, at worst racing over which exit code actually takes effect. The guard makes "only the first shutdown trigger does anything" true for every combination of triggers, not just the one that happened to be written defensively first.
Breaks if: nothing yet.

## Shutdown flush: correcting an unverified claim from earlier this stage — `producer.disconnect()` alone does not reliably surface a flush failure

Chose: call `producer.flush({ timeout: 5000 })` **explicitly and separately**, before `producer.disconnect()`, and branch the exit code on whether `flush` itself throws.
Over: wrapping only `producer.disconnect()` in try/catch and using its rejection as the signal that flushing failed (what this file proposed earlier in this stage's design, before writing the code).
Because: traced deeper into the client than the earlier design pass did. The KafkaJS-compat `disconnect()` calls the raw `Producer.prototype.disconnect(timeout, cb)`, whose actual body is `this.flush(timeoutInterval, function() { self._disconnect(cb); })` — note that inner callback takes no `err` parameter and calls `_disconnect(cb)` unconditionally. A flush that times out or fails inside that call is **silently discarded**; `disconnect()`'s own promise resolves or rejects based only on the native teardown step afterward, not on whether the flush actually finished. So the earlier plan ("wrap `disconnect()`, exit 0 vs 1 based on whether it throws") would have reported a clean shutdown even when messages were dropped on the floor. Calling `producer.flush({ timeout })` directly first uses the one method whose own promise is documented to reject on a real flush timeout (`@throws {KafkaJSTimeout} if the flush times out`), giving an honest signal before `disconnect()` (now flushing an already-empty queue, a fast no-op) runs.
Breaks if: nothing yet — recorded as a correction, not a new discovery about the requirements, so a future reader sees the wrong path was considered and rejected for a specific, verified reason rather than never having been considered at all.

## librdkafka's own logs routed through the ingester's structured JSON, not the client's default logger

Chose: a `logger` object passed into the `Kafka`/producer config, implementing the four methods (`info`/`warn`/`error`/`debug`) the client's `loggerTrampoline` calls, each forwarding into the ingester's existing `log()` helper.
Over: the client's built-in `DefaultLogger`.
Because: this is an observed problem, not a hypothetical one — Stage 1's own console output already showed lines like `{ message: 'Producer connected', name: 'rdkafka#producer-1', fac: 'BINDING', timestamp: ... }`, which is `DefaultLogger.info()`'s `console.info({ message, ...extra })` (confirmed directly in `_common.js`), util.inspect-formatted, not JSON, and shaped nothing like the ingester's own `{level, msg, ts, ...fields}` lines. Left alone, every future stage's log output has two incompatible shapes side by side. The client's `loggerTrampoline` routes both its own JS-level events and native librdkafka log callbacks through whatever `logger` is configured, so one adapter object covers both sources.
Breaks if: nothing yet.
